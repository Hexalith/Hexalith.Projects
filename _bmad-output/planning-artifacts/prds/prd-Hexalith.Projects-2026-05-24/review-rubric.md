# PRD Quality Review — Hexalith.Projects (2026-09-08, third revision)

## Overall verdict

The third revision verifies nearly every closure it claims: §0 now says what `status: final` means, A-3 has no fallback and names the reader-set delta query, §5 carries per-entry list/resolution state and the multi-input `Denied` exception that FR-13 now matches, FR-25 gives the Selection Evidence step an FR with a §2.3 class and an NFR-8 bound, FR-1/FR-7/FR-14/FR-15 state their authority level, the Administrator's restore-with-creation and replacement paths are made executable by the accepted self-inclusion trade-off and the no-creator-grant rule, "Preview body" is defined, SM-2/SM-3 are release-acceptance checks, and the counter-metrics have proxies. The authority model now holds together on the Project User and Administrator paths; what it does not yet hold together is the third actor: the Service/Workflow Caller row written to close last pass's gap grants FR-1 creation that FR-1's own text forbids twice, and the read/manage split's cost to a read-only Project User (no new Conversation can ever join the Project) is a consequence the PRD never names. The document is still a product contract in shape and proportion, with §2.1's fifth bullet and FR-8's fourth bullet the two places where rule and mechanism are fused.

## Decision-readiness — adequate

The decisions are decisions and now carry their trades all the way down: §2.1 names the accepted Administrator self-inclusion trade-off in so many words ("Accepted trade-off: a Tenant Project Administrator who already reads a Folder and binds it to a Project later holds ordinary Folder-derived Project User authority on Chatbot; that binding is audited with a self-inclusion flag rather than rejected"), §0 resolves the `final`-versus-unapproved tension by defining what final means, A-3's revisit is now honest ("there is no degraded fallback; if any capability is missing, the affected FRs are not releasable under NFR-11"), and §2.3 still refuses a smaller release.

One trade-off remains unnamed. §2.1 grants Folder read "read authority only: open, list, resolution, context, explanation, refresh, Conversation-start setup, and own-task inspection", while FR-6 requires "manage on the Project Folder" to link a Conversation and FR-14 requires "manage on the chosen Project's Folder" to confirm a candidate. A Project User with read only can therefore open a Project, retrieve FR-20 setup, and see FR-12 candidates, but can never attach a new Conversation to the Project by any path; §8's "eligible resumption" requires "an existing Conversation already associated with an Active Project", so a read-only user contributes no SM-8 numerator either. That may be the intended meaning of "read", but the PRD presents the split as a security anchor and never says that read-only collaborators are view-only on Chatbot.

### Findings

- **medium** Read-only Project Users cannot start new work and the PRD does not say so (§2.1 fifth bullet; FR-6 first bullet; FR-14 fifth bullet; §3.2 Project User row; UJ-1) — read grants Conversation-start setup but every path that associates a new Conversation with a Project (FR-6 link, FR-14 confirmation, FR-15 creation of a different Project) needs manage. The consequence is that Folder readers are spectators on Chatbot. *Fix:* add one sentence to §2.1 or §3.2: "A read-only Project User may open, resume already-linked Conversations, and inspect, but cannot attach new Conversations, Files, or Memories; this is accepted so that Folder manage remains the single mutation gate."
- **low** Administrator association actions on CLI/MCP are gated but the role row does not say it (§3.2 Tenant Project Administrator row "(Web/CLI/MCP)"; §2.1 "on CLI and MCP every association is an Inferred Association whose confirmation stays disabled until the same gates pass") — FR-7/FR-8/FR-11 by an Administrator are associations, so on CLI and MCP they are disabled until the consequential-MCP gates pass, unlike archive/restore which the Tenant Operator row gates explicitly. *Fix:* add "administrative associations on Web; on CLI and MCP once §9 A-7 holds and the consequential-MCP gates pass" to the Administrator row.

## Substance over theater — strong

Unchanged from the prior pass: no persona furniture, NFRs are numbers (NFR-5, NFR-7, NFR-8 now including "Selection Evidence expires after 5 minutes"), the Vision is specific to this module, and the counter-metrics now each carry a measurable proxy (SM-C1 "the share of Inferred Associations bound without FR-14 confirmation is zero in every window"; SM-C2 delegates to SM-3; SM-C3 "completions reported before Read-Model-Confirmed Completion stay at zero"). FR-25 is a real capability with four testable consequences, not a section added to satisfy a reviewer.

## Done-ness clarity — adequate

Up from thin. The two highs are closed on the text as it stands: §2.1 states creation needs "no prior Project authority", FR-1 says "Any Project User can create", FR-14 requires "manage on the chosen Project's Folder and read on the Conversation" and routes an already-linked Conversation to FR-7; FR-8's fourth bullet gives the Administrator path its own rule (coarse `NoLoss`/`Loss`/`Gain` class, self-inclusion flag, "a same-name Folder created on an Administrator's behalf is requested with no creator grant, leaving the permitted set empty until Folders grants access"), so Morgan's UJ-5 can be executed. FR-7 states both sides' authority, FR-6's move sentence reads "is classified as a move", FR-13 matches §5, and FR-25 defines enumeration scope, binding, single use, and rejection.

Three things are newly broken or newly exposed by the new text. First, the Service/Workflow Caller row added to §3.2 says the caller "may perform reads, FR-3 setup updates, and FR-1 creation with a supplied Folder the actor manages" and "never receives or consumes a Confirmation Artifact or Selection Evidence and therefore never links, confirms, or creates a Folder". FR-1 says binding an existing Folder "is actor-selected (FR-25) or an inferred binding confirmed under FR-8/FR-15; it is never implicit", so a caller that can hold neither evidence nor an artifact cannot supply a Folder; and FR-1 says that when no Folder is supplied Projects "requests create-only same-name Folder creation ... on every request shape including the historical name-only one", so a caller that never creates a Folder cannot omit one either. The row grants a capability FR-1 forbids in both directions, and the "therefore" is a non sequitur because same-name creation inside FR-1 needs no artifact at all. Second, FR-12 draws candidates from "Only Active, read-model-confirmed Projects" and the glossary defines a Candidate Project as "An authorized Project", which under §2.1 means read, while FR-14 confirmation and FR-25's enumeration ("limited to Projects on whose Folder the actor holds manage") require manage; Chatbot will present candidates the actor cannot accept. Third, FR-25 makes Selection Evidence "single-use" and rejects a "consumed" one with `RequestPreview`, while FR-6/FR-9/FR-10 say "a lost response recovers through `PollTask` or an equivalent Idempotency Key retry"; the equivalent retry carries the consumed evidence, so the order of evaluation decides whether lost-response recovery works, and the PRD does not state it.

### Findings

- **high** Service/Workflow Caller creation contradicts FR-1 in both directions (§3.2 Service/Workflow Caller row; FR-1 second bullet; §2.1 "Historical unversioned name-only creation compatibility"; NFR-10) — the row grants "FR-1 creation with a supplied Folder the actor manages" but the caller can carry neither Selection Evidence nor a Confirmation Artifact, which FR-1 requires for any existing-Folder binding; and the row says the caller "never ... creates a Folder" while FR-1 mandates same-name creation "on every request shape including the historical name-only one". As written the caller cannot create a Project at all, and the historical name-only compatibility path (a binding §2.1 decision) has no executable caller if it is a service integration. *Fix:* decide and state one of: (a) a Service/Workflow Caller may create with no Folder supplied and Projects performs same-name creation naming the original actor as sole manager (drop "creates a Folder" from the row's never-list and restrict it to "never binds an existing Folder"); or (b) Service/Workflow Caller creation is out of v1 and the historical name-only shape is accepted only on the actor's interactive session. Then make FR-1's second bullet say which.
- **medium** Resolution candidates are read-authorized but only manage-authorized Projects can be confirmed (FR-12 second bullet; §4 Candidate Project "An authorized Project"; FR-14 fifth bullet; FR-25 first bullet; SM-7) — a read-only actor receives a `SingleCandidate` or `MultipleCandidates` they cannot accept, FR-14 presents it with "explicit accept and decline actions", and the episode counts against SM-7. *Fix:* state in FR-12/FR-13 either that candidates are limited to Projects on whose Folder the actor holds manage (aligning with FR-25), or that read-only candidates are returned with a safe reason code (`ReadOnlyCandidate`) and excluded from FR-14's accept action and from SM-7's denominator.
- **medium** Single-use Selection Evidence defeats idempotent lost-response recovery unless evaluation order is stated (FR-25 third and fourth bullets "single-use" / "consumed ... is rejected with `RequestPreview`"; FR-6 second bullet; FR-9 fifth bullet; FR-10 second bullet; FR-1 seventh bullet "Equivalent Idempotency Key retries return the original task") — an equivalent retry of an actor-selected link carries evidence the first admission consumed. *Fix:* add to FR-25: "Consumption is recorded against the admitted Durable Task; an equivalent Idempotency Key retry resolves to that task before evidence is re-validated, so a lost response never demands a new pick." The same sentence covers Confirmation Artifacts in §5.
- **medium** Administrator Folder replacement is still called actor-selected, which FR-25 cannot produce for an Administrator (FR-23 second bullet "an actor-selected authorized replacement"; FR-25 header "A Project User can pick" and first bullet "Folders on which `Hexalith.Folders` confirms manage at pick time"; §2.1 "Project User authority is evaluated only on Chatbot sessions"; FR-8 fourth bullet) — FR-8 correctly makes the Administrator path a Preview-and-confirmation (inferred) binding with a coarse delta class, but FR-23 uses the defined term "actor-selected" for the same act, and FR-25's Web hosting ("Chatbot and Web in v1") has no eligible user because Project Users are Chatbot-only and Administrators fail the manage check at pick time. *Fix:* in FR-23 write "a replacement chosen by the actor: for a Project User, Selection Evidence under FR-25; for a Tenant Project Administrator, an inferred binding confirmed under FR-8"; in FR-25 either drop Web from v1 hosting or say which role uses it there.
- **low** Audit records the re-anchoring delta as counts in FR-21 but as a coarse class in FR-8 (FR-21 first bullet "Folder re-anchoring with its permitted-set delta as counts"; FR-8 fourth bullet "audited under FR-21 with that class and a flag") — both are Safe Metadata, but downstream needs one field. *Fix:* FR-21: "with its permitted-set delta as counts for a Project User replacement and as the coarse class plus self-inclusion flag for an Administrator replacement or legacy binding".
- **low** A Project User cannot restore an Archived Project whose Folder is missing, by construction (FR-23 header and second bullet "If the prior Folder is invalid or missing"; FR-8 header "A Project User sets the single Project Folder within ... FR-23 restore"; §2.1 Folder-derived authority) — when the prior Folder no longer exists, nobody holds Folder read on it, so the Project's permitted set is empty and only a Tenant Project Administrator can act; the Project User path applies only when the prior Folder exists but is invalid (for example claimed by another Active Project). *Fix:* say so in FR-23: "When the prior Folder no longer exists, the Project has no permitted Project Users and restore is a Tenant Project Administrator operation."

## Scope honesty — adequate

§2.4 still does the work, A-3 is now honest about having no fallback, A-5's default is stated with its operator cost (§3.2 Tenant Operator "identifies Projects by opaque identifier unless holding inspection authorization"), and A-6/A-7 carry executable revisit conditions. The read-only consequence above is the one inference left to the reader; two smaller ones follow.

### Findings

- **low** "Any Project User can create" has no meaning before the first Project (FR-1 second bullet; §3.2 Project User row "Read authority from Folder read (§2.1) over their permitted Projects"; §4 roles entry) — a Project User is defined by Folder read on some Project, so an actor with no permitted Projects is not yet one, and §2.1's "requires no prior Project authority" is the real rule. *Fix:* define Project User as "any authenticated actor on a Chatbot session in the Tenant" and let permitted Projects narrow what they can read.
- **low** An Active Project with an empty permitted set is now possible and the invariant's word "authorized" needs its meaning fixed (FR-8 fourth bullet "leaving the permitted set empty until Folders grants access"; §2.1 "before exactly one authorized Project Folder is bound"; NFR-4; FR-16) — after an Administrator restore-with-creation the Project is Active and visible only through Tenant-role surfaces. That is acceptable, but "authorized Project Folder" in the invariant must mean verified, same-Tenant, and exclusively bound, not readable by any Project User, or the invariant appears violated. *Fix:* add to §4 Project Folder or §2.1: "'authorized' here means verified in Folders, same-Tenant, and bound to no other Active Project; it does not require a non-empty permitted set."

The pressure points that remain are §2.1's fifth bullet, now about 230 words of authorization design in a "Planning Decisions" list, and FR-8's fourth bullet, which grew rather than shrank: it now carries the coverage rule, the counts disclosure, the coarse-class vocabulary, the self-inclusion flag, the no-creator-grant creation, and the reader-set evidence binding in one paragraph. ### Findings
