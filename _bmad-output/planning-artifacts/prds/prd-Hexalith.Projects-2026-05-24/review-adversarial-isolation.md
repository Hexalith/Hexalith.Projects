# Adversarial Review — Isolation and Authority — Hexalith.Projects

Reviewed: `prd.md` (third 2026-09-08 revision, 25 FRs) and `addendum.md`, against the second 2026-09-08 adversarial review at this path. Lens: hostile delegated caller (Service/Workflow Caller with a real actor's delegated scope), compromised Project User session holding Folder manage, multi-Tenant operator holding Tenant-role authority in several Tenants, and a Chatbot bug or autonomously acting model that calls Projects APIs on the user's session without a human gesture.

## Overall verdict

The third revision closes every one of the fourteen prior findings as written: subject read in the owning system is required at FR-6/FR-7/FR-9/FR-10/FR-14, Project User replacement fails closed on any reader loss, the Administrator path is the single reducing path with class, flag, digest, and audit, A-3 names the upstream capabilities with no degraded fallback, creation names the original actor as sole manager on every request shape, FR-25 makes Selection Evidence a pick inside a Projects-owned component, initial Folder set is manage everywhere, reference titles are gated on the owning system, the legacy inventory has a scoped name exception, and the residual disclosures are stated as accepted. No critical remains. But the revision's own choices open two high holes. First, FR-25's rationale ("there is no mint API a caller can invoke on the actor's behalf") concedes that a session-bound server nonce transported by Chatbot is not proof of a human pick, and Confirmation Artifacts are exactly such a nonce with exactly such an API: a Chatbot bug still self-confirms every Inferred Association and every consequential action, so the FR-14 gate that FR-25 was built to protect is as weak as the mint step was. Second, the "accepted trade-off" for Administrators is described as an incidental self-inclusion, but FR-8 lets a Tenant Project Administrator re-anchor any Active Project in the Tenant to any Folder, which is a self-service takeover and Tenant-wide Descriptive Metadata disclosure path that voids A-5's guarantee that "Tenant-role actors obtain it by no other path", detectable only by the same role class through per-Project audit. Below those, the coarse delta class is still a per-principal ACL oracle and FR-21 stores the exact counts anyway; the selection component's trust boundary against its own Chatbot host is unstated; the no-creator-grant rule pushes the self-grant out of the flag's view; and three internal contradictions (Service/Workflow Caller creation, Web hosting of FR-25 against Chatbot-only Project User authority, FR-8 header against FR-23) will be resolved by implementers in the permissive direction. The model is now sound where it is explicit; the findings are where it is silent about its own hosts and roles.

## Findings

- **high** Confirmation Artifacts retain the self-confirm weakness FR-25 was written to remove from Selection Evidence (§2.1, §4 Confirmation Artifact, FR-14, FR-15, FR-6, FR-7, FR-11, A-6, addendum §1, §2, §6) — The revision's justification for FR-25 is that Selection Evidence "is minted by the actor's pick, never by an API call a caller makes on the actor's behalf" and, in the addendum, "there is no mint API a caller can invoke on the actor's behalf. A client-asserted flag is not acceptable." That is a statement that a server-issued, session-bound, single-use token returned to Chatbot and sent back by Chatbot proves nothing about a human, because Chatbot holds the session on both legs. A Confirmation Artifact is precisely that token: Preview returns it to the "dual-principal adapter (Chatbot, Web, CLI) that carries that session", confirm consumes it, and the only thing standing between a Chatbot bug and a bound Inferred Association is the sentence "cannot originate or self-confirm", an obligation Projects cannot observe. Attack: Chatbot receives `SingleCandidate X` (no `ConversationLinked`), calls Preview for FR-6/FR-14 on the user's session, receives the artifact, and calls confirm without rendering the comparison FR-14 requires. Every FR-14 consequence is satisfied from Projects' side; SM-C1 ("the share of Inferred Associations bound without FR-14 confirmation is zero") is unmeasurable because Projects records a confirmation. The same path self-confirms archive (FR-4), unlink (FR-11), move (FR-7), and proposal creation (FR-15). A-6's fallback ("until the FR-25 component exists on a surface, every additive link ... is an Inferred Association requiring confirmation") therefore routes the case FR-25 hardened onto the weaker gate. *Fix:* Apply the FR-25 mechanism to confirmation: state in §4 Confirmation Artifact and FR-14 that on Chatbot the accept/decline and confirm/cancel controls are rendered by the same Projects-owned interactive component, that the artifact is consumed only by that component's submission on the actor's session, and that Chatbot's adapter transports Preview bodies but never the artifact itself. Until that component exists, make Chatbot's non-self-confirmation a named NFR-11 release-evidence item in addendum §6 (an authenticated test that the confirm path is unreachable without a UI event) rather than an unverifiable obligation.

- **high** The accepted Administrator trade-off is a Tenant-wide takeover and Descriptive Metadata path that voids A-5, with detection only by the same role class (§2.1, §3.2, §4 Descriptive Metadata, FR-8, FR-21, FR-22, FR-23, A-3, A-5) — §2.1 words it narrowly: "a Tenant Project Administrator who already reads a Folder and binds it to a Project later holds ordinary Folder-derived Project User authority on Chatbot; that binding is audited with a self-inclusion flag rather than rejected." But FR-8's header grants the capability broadly: "a Project User with manage authority on both Folders or a Tenant Project Administrator can replace it through Preview and confirmation", for any Active Project, not only quarantined or archived ones, and "A Tenant Project Administrator replacement or legacy binding is the only path that may reduce a permitted set". Attack: an Administrator lists every Project by opaque id (FR-5 on Web), re-anchors P from F to a Folder G they manage (class `Loss`, flag set), opens Chatbot as a Project User of P, reads Project name, Setup bodies, and every reference title they hold owner-system read on, updates Setup (FR-3, no Preview), and re-anchors P back to F (class `Gain`, flag clear). §4 says Descriptive Metadata is served to Tenant-role actors only "with separate descriptive-metadata inspection authorization ... and Tenant-role actors obtain it by no other path"; A-5 says until that permission exists "Descriptive Metadata stays Project-User-only". This is the other path, and it needs no inspection authorization. Variant: re-anchor P to a Tenant-default-read Folder (`Gain`) and every Tenant member becomes a Project User of P. Detection: the FR-8 audit rows are readable under FR-22 "per Project" by Tenant Operators and Administrators, that is, by the actor's own role class; the F readers who lost P are no longer permitted for P and cannot read its audit, and nothing notifies them. The Chatbot reads that follow are not audited at all (reads are not FR-21 events), so the bypass is cheaper to audit than the A-5 inspection it replaces. *Fix:* Narrow FR-8 so an Administrator replacement of an Active Project whose current Folder has at least one manager requires a Confirmation Artifact consumed by one of those managers (two-party), and reserve unilateral Administrator binding for the cases with no current manager (quarantined legacy, archived with missing Folder). Additionally record the binding Administrator on the Project and emit an FR-21 `AdministratorSelfAccess` event the first time that actor's Folder-derived authority on that Project is exercised on Chatbot (this also closes the time-of-check gap in the medium finding below). Restate A-5 and §4 to admit the residual path honestly if the two-party rule is refused.

- **medium** The coarse delta class is still a per-principal ACL oracle over Folders the Administrator cannot read, and FR-21 stores the exact counts anyway (FR-8, FR-21, FR-22, A-3) — FR-8: the Administrator Preview "discloses the delta as a coarse class (`NoLoss`, `Loss`, `Gain`)". `NoLoss` means readers(F) ⊆ readers(G). Attack: the Administrator manages a scratch Folder G whose readers they control (the accepted trade-off permits exactly this); set readers(G) = everyone in the Tenant except x, Preview F→G, and `Loss` iff x reads F. One Preview per principal enumerates F's reader set for any Folder in the Tenant. FR-8 says "every such Preview ... is audited under FR-21 with that class", which is detective only and, per the high finding above, readable by the same role. Worse, FR-21 contradicts FR-8: audit covers "Folder re-anchoring with its permitted-set delta as counts". If the completion row carries counts, the Administrator reads |readers(F) \ readers(G)| straight from the FR-22 audit view after one real re-anchoring, and the coarsening in Preview is theater. The three-value vocabulary also cannot express a replacement that both loses and gains readers, so the class an implementer reports for the common case is undefined. *Fix:* Disclose the class to an Administrator only when they hold Folders read on the source Folder (then they can read its ACL in Folders anyway); otherwise Preview states `PossibleLoss` with no coverage computation and the Administrator confirms blind. Change FR-21 to "delta as counts for Project User replacement; as class for Tenant-role re-anchoring", make the class a set (`Loss`, `Gain` may co-occur), and cap Administrator FR-8 Previews per Project per hour under NFR-7 with an audit event on the cap.

- **medium** The Projects-owned selection component has no stated trust boundary against its own Chatbot host, and Chatbot is not a FrontComposer host (FR-25, §2.1, §4 Selection Evidence, A-6, addendum §1, §1.1, §6) — FR-25 asserts that Selection Evidence "is minted by the actor's pick, never by an API call a caller makes on the actor's behalf". Any pick becomes a request from the browser to Projects; that request is the mint API, and the only question is who else can send it. The component is "hosted via FrontComposer on Chatbot and Web" (A-6), inside Chatbot's page, on Chatbot's origin, under Chatbot's session. Chatbot's page script can drive the component's DOM or replay its request; Chatbot's server, holding the same delegated session, can call the same endpoint if the component's transport is authenticated by session alone. Nothing in FR-25, A-6, or the addendum says what the component's call carries that Chatbot cannot obtain (a component-scoped anti-forgery token issued by Projects, an isolated origin, a FrontComposer-attested UI event). Addendum §6 lists Chatbot obligations for candidate presentation and artifact audience and still none for the selection component. And addendum §1.1 says "FrontComposer/platform hosts own Web, MCP, and CLI runtime composition"; Chatbot is not a FrontComposer host, so "hosted via FrontComposer on Chatbot" names a composition that no artifact owns. *Fix:* In FR-25 and A-6, state the mechanism: the component runs on a Projects-controlled origin (or FrontComposer-isolated host) and its mint request carries a Projects-issued component token bound to the rendered enumeration that is never returned to the adapter; the Chatbot adapter receives only the resulting Selection Evidence. Add to addendum §6 that Chatbot must not automate, script, or proxy the component, with an NFR-11 test. Add Chatbot to addendum §1.1 or rewrite A-6 to name the actual host.

- **medium** "No creator grant" relocates the self-grant to Folders where the self-inclusion flag never fires, and a no-manager Folder has no stated grant path (FR-8, FR-23, §2.1, A-3) — FR-8: "a same-name Folder created on an Administrator's behalf is requested with no creator grant, leaving the permitted set empty until Folders grants access", and the flag is raised "when the Administrator is in the target Folder's reader set" at Preview and completion. Attack: the Administrator restores P with same-name creation (flag clear, set empty), then grants themselves read in Folders. Who can grant on a Folder with "no manager" (A-3)? Only a Folders-level Tenant administrator, which in practice is the same person or role; A-3 names no such capability, so either the grant path does not exist (P is a permanently Active Project with an anchor nobody can administer, and the create-only name is squatted for the Tenant's lifetime under A-2) or it is the Administrator's own Folders authority, in which case the self-inclusion flag, evaluated only at Preview and completion, records `false` for the very case it exists for. The rule moves the self-grant out of Projects' audit rather than preventing it. *Fix:* Either request the created Folder with the Administrator as sole manager and set the flag `true` by definition (honest and auditable), or state in A-3 who may grant on a no-manager Folder and require Folders to emit that grant as a receipt Projects audits. In both cases add the `AdministratorSelfAccess` event proposed in the second high finding so the flag is evaluated at first use, not only at binding.

- **medium** Service/Workflow Caller creation is unsatisfiable as written and will be implemented as the implicit binding FR-1 forbids (§3.2, FR-1, FR-15, FR-25) — §3.2: a Service/Workflow Caller "may perform reads, FR-3 setup updates, and FR-1 creation with a supplied Folder the actor manages ... never receives or consumes a Confirmation Artifact or Selection Evidence and therefore never links, confirms, or creates a Folder". FR-1: "Binding an existing Folder is actor-selected (FR-25) or an inferred binding confirmed under FR-8/FR-15; it is never implicit." A supplied Folder from a caller that can hold neither Selection Evidence nor a Confirmation Artifact cannot be bound. And FR-1 says that when no Folder is supplied "Projects requests create-only same-name Folder creation ... on every request shape including the historical name-only one", so a delegated caller sending the legacy name-only shape creates a Folder, which §3.2 says it never does. An implementer will resolve this by treating a delegated caller's supplied Folder as an implicit binding, which is the one path FR-1 rules out, and the legacy shape gives a hostile delegated caller a Folder-creation primitive under the actor's name. *Fix:* Pick one: remove FR-1 from the Service/Workflow Caller row and reject creation without an interactive session with `RequestPreview`; or define delegated creation as admitting a task that stays `NeedsAttention` until the original actor binds the Folder interactively (FR-25 or confirmation), and state that the legacy name-only shape is accepted only on interactive adapters.

- **medium** Project User authority is "evaluated only on Chatbot sessions" while FR-25 and A-6 host the Project User picker on Web, and adapter-to-surface mapping is unstated (§2.1, §3.2, FR-25, A-6, A-7, §6.6) — §2.1: "Project User authority is evaluated only on Chatbot sessions; Tenant Operator and Tenant Project Administrator authority ... applies on Web, CLI, and MCP". FR-25: "The component is hosted only on adapters the platform registers as interactive (Chatbot and Web in v1)" and enumerates "Projects on whose Folder the actor holds manage", which is Project User authority evaluated on Web. Selection Evidence "minted on another surface is rejected", so Web-minted evidence is usable only on Web, where no Project User FR is available. Either the Web hosting is dead text or Web silently becomes a Project User surface for one operation, and §3.2's "confirmation of a resolution or proposed creation, which is Chatbot-only" has no counterpart forbidding the rest. The separation "never combined ... in one session" is enforced by surface, and surface is whatever the adapter credential is registered as; nothing says an adapter maps to exactly one surface, so a Chatbot deployment that also registers as an MCP host is both, and an actor with Folder manage and Tenant-role authority holds both authority sets on that session. *Fix:* Drop Web from FR-25 and A-6, or make Web an explicit Project User surface in §2.1 and §3.2 with the full FR list. State in §2.1 that each registered adapter credential maps to exactly one surface and that a credential registered for two surfaces is rejected at every authorization decision.

- **medium** Project Context is keyed by Project, not by Conversation membership, so cross-Project contamination is entirely in Chatbot's hands (FR-16, FR-20, FR-12, UJ-4, SM-C1, addendum §6) — FR-16: "Chatbot can request Project Context for an Active Project"; FR-20: "the subset of Project Setup needed to start or resume a Conversation", bound to a `projectVersion`. Neither takes the Conversation. A Chatbot bug that ignores FR-12's reasons, or a model that picks a Project, requests context for X and injects it into Conversation C that has a confirmed membership in P. UJ-4 promises "Unconfirmed candidates ... and unrelated Tenant data never enter the active context", but Projects cannot enforce it because it never learns which Conversation the context is for. This is within the actor's own read authority, so it is a contamination and intent failure rather than an escalation, but it makes SM-C1 and UJ-4 unverifiable from Projects' evidence. *Fix:* Add an optional Conversation identity to FR-16 and FR-20; when supplied and the Conversation has a confirmed membership in a different Project, return `Unavailable` with `SelectAlternative` and no Setup; when the Conversation has no membership, serve as today. Require Chatbot to supply it for existing Conversations in addendum §6.

- **medium** Setup instructions are the highest-leverage mutation for AI behavior and the only one a delegated caller performs with no interactive gate, and the audit does not name the caller kind (FR-3, §3.2, FR-16, FR-20, FR-21) — FR-3: "Updates are admitted as an idempotent Durable Task without Preview". §3.2 allows a Service/Workflow Caller "FR-3 setup updates" with the actor's delegated scope. Setup carries "user-facing instructions" that FR-20 feeds into every Conversation start. A hostile delegated caller, or a compromised session, rewrites the instructions of every Project the actor manages; every subsequent Conversation in those Projects is steered. FR-21 audits "task admission and terminal outcome" so the version bump is recorded, but no Setup-specific event names whether the admitting credential was interactive or delegated, and FR-18 reports only "policy-driven inclusion changes", not instruction changes, so users see nothing. *Fix:* Add an FR-21 event for Setup instruction changes carrying actor, caller kind (interactive or delegated per A-7), and the field class changed; make FR-20 report `SetupChangedSinceLastStart` as a component reason when the instruction version differs from the Conversation's last admitted one; consider requiring Preview for instruction changes from a Service/Workflow Caller.

- **low** FR-8's header and FR-23 disagree on Project User restore authority, and the permitted set of an Archived Project with a missing Folder is undefined (FR-8, FR-23, §4 permitted set) — FR-8: "A Project User sets the single Project Folder within FR-1 creation or FR-23 restore with manage on that Folder". FR-23: "Only an actor with FR-8 replacement authority may restore with a replacement or newly created Folder", which is manage on both Folders plus reader coverage. When the prior Folder is missing, manage on it cannot be held and its reader set is undefined, so a Project User restore with replacement is either impossible (FR-23 reading) or single-manage (FR-8 reading); an implementer will treat the missing Folder's readers as empty, coverage as vacuously true, and let any Folder-manage holder claim the Project. *Fix:* State that an Archived Project whose Folder is missing or unauthorized has an empty permitted set, that only Tenant-role actors may restore it (hitting the second high finding's two-party rule), and align FR-8's header with FR-23.

- **low** Pseudonymous actor identifiers in Safe Diagnostic Export are not stated to be Tenant-salted, so a multi-Tenant operator correlates people across Tenants (§4 Safe Metadata, FR-24, addendum §3) — "actor identifiers in Safe Diagnostic Export are pseudonymous" and the addendum requires "pseudonymous actor identifiers". A deterministic pseudonym of the platform user id is identical in every Tenant's export; an operator holding FR-24 authority in Tenants A and B links the same person's activity across both, which §2.1's cross-Tenant predicate is meant to prevent. *Fix:* Require pseudonyms derived with a per-Tenant secret so the same actor yields unrelated identifiers in different Tenants' exports, and say the same for the opaque identifier mapping in Safe channels.

- **low** Read-only Project Users can never make a Conversation belong to a Project, which pressures implementers to relax FR-6 to Folder read (§2.1, FR-6, FR-12, FR-14, FR-20, SM-8) — Folder read grants "Conversation-start setup" (FR-20) but linking and FR-14 confirmation require "manage on the chosen Project's Folder". A read-only member starts Conversations with P's Setup that are never members of P; FR-12 returns candidates they cannot confirm; SM-8's "eligible resumption" excludes all of them. The obvious relaxation is to let read-holders link, which without care reopens the capture attack the revision closed. *Fix:* Either state the limitation as accepted in §2.1 and §3.2, or allow an actor-selected additive link (FR-6, FR-10) under Folder read when the actor holds owner-system read on the subject, keeping move, unlink, File link outside the Folder, and replacement at manage; the subject-read requirement is the guard that matters.

- **low** The legacy inventory name exception is gated on role, not on the A-5 permission, and its audit granularity is unstated (FR-22, A-5, §2.4) — FR-22 makes the name readable "as a narrowly scoped and audited exception to A-5", so it works even while A-5's default ("Tenant-role actors receive Safe Metadata only") is in force. It is one read returning every quarantined Project's name in the Tenant; A-5 requires inspection to be "audited per Project", and FR-22 does not say whether one inventory read produces one audit row or one per Project. *Fix:* Gate the exception on the A-5 permission once it exists (role-only until then, stated as such), and require one FR-21 inspection event per Project returned.
