# Authority, isolation, and recovery review

Reviewed November 20, 2026. The PRD distinguishes opening a Project from admitting a Conversation and requires durable audit before retained v1 name disclosure. Two cases still give conflicting directions at the Folder authorization boundary. Two others affect legitimate reassociation and candidate selection.

## Findings

- **High — Create-only Folder recovery lacks an owner guarantee.** FR-1 requires a name collision to fail closed and says creation “never binds a pre-existing Folder” (prd.md line 213). FR-19 repeats this rule at line 463. A-2 instead allows Projects to “pre-check” when Folders cannot guarantee create-only behavior (line 597). An initial absence check cannot establish which Folder the owner created if another same-name creation completes before provisioning. *Fix:* Require an owner result that guarantees this request created the Folder. If the owner cannot give that guarantee, keep the Project inactive and use the existing recovery or explicitly authorized binding path.
- **High — The restore criteria disagree about who can replace a missing Folder.** FR-23 assigns a missing or unreadable prior Folder to “a Tenant Project Administrator” (prd.md line 510). Its testable consequence then includes “for a Project User, Selection Evidence under FR-25” in the “invalid or missing” case (line 515). A Project User can select a target, but a pick supplies no proof of manage authority on the missing source Folder. *Fix:* State the Administrator-only rule in the missing/unreadable acceptance case. Limit Project User replacement to a verifiable prior Folder where the actor manages both Folders and the target covers the existing readers under FR-8.
- **Medium — A detached Conversation has conflicting source-Project checks.** FR-7 says “after a confirmed unlink, target and Conversation only” (prd.md line 294), then requires rejection when “either Project or the Conversation cannot be authorized” (line 297). FR-11 explicitly waives prior-Project authorization for that detached case (line 347). A user allowed to relink a Conversation could be refused solely because they cannot read its former Project. *Fix:* Condition the prior-Project read check on current membership. After a confirmed unlink, retain the opaque prior receipt, target manage authority, and Conversation read authority.
- **Medium — A read-only sole candidate both receives and lacks an accept action.** FR-12 requires “no accept action” for a read-only actor (prd.md line 373). FR-14 requires “explicit accept and decline actions” for a sole candidate without that qualification (line 395). The addendum repeats the unqualified rule at line 144. This yields incompatible acceptance tests for a user who can read the candidate but cannot manage its Folder. *Fix:* Show accept only for a candidate that passes the independent manage and subject-read checks. Preserve the read-only presentation and leave confirmation unavailable for that candidate.
