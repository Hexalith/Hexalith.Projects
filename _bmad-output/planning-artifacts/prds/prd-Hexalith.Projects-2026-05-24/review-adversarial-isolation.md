# Adversarial Review — Isolation and Authority — Hexalith.Projects

## Overall verdict

This PRD talks like a fail-closed isolation contract and then leaves the enforcement hinges as client honor system. The confirmation boundary, Conversation membership invariant, and actor-authorization model can be satisfied on paper while still silently attaching work, moving membership without a move, or assembling another actor’s workspace. Tenant-scoped metadata-only language is real; it is not a substitute for same-Tenant reference invariants, an exclusive Folder anchor, or a field allow-list that keeps Setup and titles out of operator/export channels.

## Findings

- **critical** Actor-selected vs inferred is not a server fact; SingleCandidate can durable-attach without FR-14 (§1, FR-6, FR-9, FR-10, FR-12, FR-14, SM-C1) — Vision asks for confirmation only “when intent is ambiguous.” FR-14 binds Preview/Confirmation solely to “When resolution returns multiple candidates” and “No candidate is silently or visually preselected.” FR-12 may return `SingleCandidate` and only says “`Unavailable` and `Denied` never return a selected candidate” — it does not forbid treating that one survivor as selected. FR-6 then admits “An explicitly actor-selected additive link uses an idempotent Durable Task without a second confirmation.” Nothing defines how the server distinguishes actor-selected from inferred. A Chatbot or delegated caller that receives `SingleCandidate` (or that watches authorization filtering collapse three matches to one, because “unauthorized or stale resources cannot become candidates”) can call `conversation.link` / file / Memory link as actor-selected. FR-13 `ProjectFolderMatched` / `FileReferenceMatched` has the same path: attach files that already belong to someone else’s Project and the only authorized hit becomes a silent membership. SM-C1 says “Do not optimize automatic attachment rate at the expense of explicit intent,” but no FR makes SingleCandidate, MetadataMatched, or resolution-originated links inferred. *Fix:* Define inferred as any association whose Project id originated in a Resolution Result, proposal, or attachment match. Require the same Confirmation Artifact as FR-14 for every inferred Conversation/File/Memory/Folder bind, including `SingleCandidate`. Treat authorization-hidden siblings as still-ambiguous (`MultipleCandidates` or `Unavailable`), never as a manufactured single hit. Reject `conversation.link` unless the request carries an actor picker artifact or a consumed confirmation, not a client `selectionMode` flag.

- **critical** Conversation unlink plus actor-selected link bypasses FR-7 and breaks exactly-one membership (FR-6, FR-7, FR-11, §2.1, §4) — §2.1 and the glossary require “A Conversation belongs to exactly one Project in v1.” FR-11 nevertheless lets a Project User or Tenant Project Administrator “unlink a Conversation … through Preview, confirmation, and an idempotent Durable Task,” which is a legal zero-Project state. After unlink, FR-6’s “Linking a Conversation already assigned elsewhere requires FR-7” does not apply, so the next “explicitly actor-selected additive link” is a silent Durable Task with no Preview binding both Projects. That is a two-step move that evades FR-7’s “Preview binds both Projects, the Conversation, actor, and current resource versions” and FR-7’s “The move is audited using metadata only.” Memlog-level intent (“changing membership requires an explicit auditable move”) is not an FR. File/Memory have the same unlink-then-silent-link path (FR-11 then FR-9/FR-10) with no move operation at all. *Fix:* Either forbid Conversation unlink (replace with FR-7 move or archive-only detach) or classify any link to a previously membered Conversation as a move: same dual-target Confirmation Artifact, same audit action, same fail-closed membership invariant. State that zero membership is not an allowed durable end state except as a transient `NeedsAttention` with the prior Project still bound.

- **high** Same-Tenant is not an invariant on links, moves, or resolution inputs (NFR-1, FR-6, FR-7, FR-9, FR-10, FR-13) — NFR-1 says every write is “Tenant-, actor-, action-, target-, and current-version-scoped,” but FR-6/FR-9/FR-10 never require the Conversation, File, Memory, or Folder to be the same Tenant as the Project. FR-7 only “fails closed when either Project or the Conversation cannot be authorized.” A delegated Service/Workflow Caller or a multi-Tenant operator that is authorized for both sides can satisfy “authorized” while linking Tenant A’s Conversation or Folder into Tenant B’s Project. Resolution from attachments (FR-13) matches “current authorized Folder/File identity” with no same-Tenant sentence. Tenant isolation then depends on sibling ACLs and hope. *Fix:* Add a fail-closed same-Tenant predicate on every reference: Project.Tenant == owner.Tenant == actor.Tenant for link, move, Folder bind/replace, restore, resolution inputs, context assembly, audit, and export. Authorization on both ends is necessary and not sufficient.

- **high** “Permitted Projects” has no grant, share, or deny model (§3.2, FR-2, FR-5, FR-16, NFR-1, SM-3) — The Project User “Read access to their own permitted Projects” and FR-2 “only data visible to the requesting Tenant and actor,” but no FR creates, lists, or revokes that permission. Jobs-to-be-done still claims “Prevent context leakage across Projects, actors, and Tenants.” SM-3 demands “Zero unauthorized or cross-Tenant disclosures” without defining intra-Tenant unauthorized. Implementers will default to Tenant-wide Project User access: any coworker can open, resolve, archive, relink, and pull FR-16 context (Setup, File/Memory identities) for every Project in the Tenant. NFR-1’s actor-scoping is then circular — scoped to an undefined permit set. *Fix:* Specify the v1 actor-authorization model (creator-only, explicit members, or inherited Tenant role) and the grant/revoke operations. Define “unauthorized” for SM-3 as any Project or reference not in that set, including same-Tenant peers. If v1 is Tenant-wide by policy, say so and drop the actor-leakage claim.

- **high** Same-name Folder creation can attach a foreign workspace (FR-1, FR-19, FR-23, addendum §5) — FR-1: “When none is supplied, Projects requests same-name Folder creation from `Hexalith.Folders`.” FR-23: if the prior Folder is “invalid or missing, Preview requires an authorized replacement or same-name Folder creation.” Neither says create-only, nor forbids binding an already-existing same-name Folder, nor forbids a Folder that is already another Project’s authorization anchor. A colliding name — or a leftover orphan from a failed create (addendum §1 “Orphan/reserved Folder recovery without automatic deletion”) — can activate Project B on Project A’s files. FR-19 “never defaults a caller-visible Project to Active before Folder completion” still allows the wrong Folder. *Fix:* Same-name means a create that fails closed on name collision. Binding an existing Folder requires an actor-selected, authorized Folder id plus confirmation that names the Folder owner and any other Project using it. Orphans stay `NeedsAttention`; they never become the implicit restore target.

- **high** The Folder is a cardinality rule, not an exclusive authorization anchor (§2.1, FR-8, FR-16, UJ-4) — §2.1: “exactly one authorized Project Folder is bound” and “The single Folder trades multi-root workspaces for a stable authorization anchor.” FR-8: “Every Active Project has exactly one authorized Project Folder.” Nothing says a Folder is bound to at most one Active Project. Two Active Projects can share the same Folders ACL, so FR-16 context, FR-13 `ProjectFolderMatched`, and File authorization are cross-contaminated while each Project still boasts “exactly one” Folder. UJ-4’s “Unconfirmed candidates, foreign payloads … never enter the active context” does not survive a shared root. *Fix:* Require exclusive Folder binding for Active Projects, or declare shared-Folder as an explicit multi-Project workspace and drop the “unambiguous workspace boundary” claim. Replacement and restore must fail closed if the target Folder is already another Active Project’s anchor.

- **high** Delegated callers can confirm and mutate if they hold actor credentials plus the artifact (§2.1, §3.2, FR-14, addendum §1.1) — §3.2: Service/Workflow Caller “follows the actor's authority and never gains autonomous confirmation or blanket mutation authority.” Addendum §1.1 requires paths to “carry real credentials and delegated service identity” and forbids “allow-all development stubs,” but never says policy evaluates only the original actor, never the workload role. FR-14 issues a Confirmation Artifact “bound to Tenant, actor, action, Conversation, candidates…” and does not require a distinct interactive Chatbot gesture or a Chatbot-only audience to consume it. A workflow that requests Preview as the actor receives the artifact and can consume it in the same hop — autonomous confirmation with extra ceremony. If admission checks the service principal, a Tenant Operator or Administrator workload expands a Project User’s authority, contradicting “Role and surface choice never expand authority; service callers act only with delegated actor authority.” *Fix:* Bind every action decision to the original actor and action; workload identity is transport, not a role. Do not return a consumable confirmation token to Service/Workflow Callers. Consumption is a Chatbot Project User interactive action; MCP/service confirmation stays denied, not merely “gated until later.”

- **high** Tenant Project Administrator reconciliation is an unbound authority expansion (FR-22, FR-1, FR-7, FR-14, FR-15, FR-23) — FR-22: “Tenant Project Administrators may perform authorized reconciliation.” No FR lists what reconciliation may change. Addendum §1 asks architecture for receipts on “Folder creation/binding, Conversation membership, File/Memory links, archive, and restore.” An Administrator can therefore finish a `NeedsAttention` create/restore/membership without the Confirmation Artifact bindings those FRs required at admission, or rewrite Conversation membership without FR-7’s dual-Project Preview. That is surface-and-role expansion of user-intent authority. FR-1’s “reconciliation never exposes an Active folderless Project” constrains Folder presence, not membership or confirmation. *Fix:* Reconciliation may only retry or compensate an already-admitted task against its original bound targets, actor, and Preview digest. It cannot add targets, change Project/Conversation/Folder ids, confirm resolution/proposal, or admit a new mutation. New intent requires a new Preview.

- **high** “Metadata-only” still ships Setup, names, and titles through operator read, traces, and export (FR-3, FR-17, FR-21, FR-22, FR-24, §2.4, NFR-1) — §2.4: Projects “does not store full transcripts, file contents, raw prompts, secrets, Memory payloads.” It does store Project Setup “user-facing instructions” (FR-3) and “stable identity and metadata” for Conversations, Files, and Memories. FR-22 lets Operators/Administrators inspect “authorized Project metadata, lifecycle state, references … and audit metadata.” FR-24 exports “from an already-authorized diagnostic view” with no field allow-list — only size/row caps. FR-21 audit includes “affected reference identifiers.” FR-17 traces omit “secrets, payloads, prompts” but not Setup text or Conversation titles. Operators and export recipients therefore get prompt-adjacent instructions and human-readable titles that SM measurement explicitly refuses (“no Conversation text, Project name, prompt”). “Metadata-only” is doing two jobs and losing both. *Fix:* Publish an allow-list: identifiers, lifecycle, versions, safe reason/freshness codes, counts. Exclude Setup instruction bodies, Project names, Conversation titles, file names/paths, Memory titles, and Preview bodies from FR-17, FR-21, FR-22, and FR-24 unless a separate content-inspection permission exists. FR-24 must name the schema, not inherit “the diagnostic view.”

- **medium** FR-6 does not inherit FR-7’s dual-membership fail-closed (FR-6, FR-7, NFR-4) — FR-7: “Failure, duplicate delivery, or lost response cannot leave two memberships silently valid.” FR-6 only says a Conversation “belongs to exactly one Project” and that an existing assignment “requires FR-7,” which is a check-then-act race. Two concurrent actor-selected links, or a link racing a move, can leave two memberships or a Conversations/Projects split brain. NFR-4’s “never silently dropped or duplicated” is about tasks, not membership. *Fix:* State the same atomic invariant on every membership mutation: at most one valid Project, fail closed, no silent dual write, lost response converges to one receipt.

- **medium** FR-3 silently changes the context-assembly policy (FR-3, FR-16, §2.1) — §2.1: “consequential actions follow the approved Preview/Confirmation boundary.” FR-3 updates “source inclusion/exclusion policy” and Conversation-start defaults with no Preview. That mutation changes what FR-16 includes on the next context read without a confirmation bound to `projectVersion`. A delegated Chatbot or compromised Project User session can widen inclusion and pull previously excluded File/Memory references into active context. *Fix:* Classify inclusion/exclusion and default-source policy as confirmation-required, or snapshot the policy into the Conversation-start Confirmation/`projectVersion` so a silent setup write cannot admit new references into an already-opened context.

- **medium** “Relink” is in the role matrix and audit list but is not an operation ( §3.2, FR-7, FR-8, FR-11, FR-21) — Project User and Tenant Project Administrator may “relink”; FR-21 audits “move, relink, Folder replacement, unlink.” The only defined retarget is FR-7 Conversation move and FR-8 Folder replace. File/Memory have link and unlink only. Implementers will invent a silent relink as unlink+link or as actor-selected FR-9/FR-10, granting Administrators a confirmation-free retarget the matrix appears to allow. *Fix:* Strike “relink” or define it as FR-7/FR-8-class Preview for every reference kind, with both old and new targets bound.

- **medium** FR-24 permission is not a disclosure control; FR-22 pagination already dumps the tenant (§2.3, FR-5, FR-22, FR-24, NFR-5, NFR-6) — §2.3: FR-22 and FR-24 “are the supported alternatives to unbounded troubleshooting access.” FR-22 is Tenant-scoped inspect of projects, references, tasks, confirmed resolution outcomes, and audit, pageable at “cap at 200” with no iteration cap against NFR-5’s 5,000 references and 100,000 audit records. FR-24’s 1 MiB / 500 / 100 caps and “no continuation cursor” therefore bound a package format, not access. Separate export authorization does not stop a CLI/MCP Operator from reconstructing the same metadata without FR-24. Chatbot exclusion is real; confidentiality of the diagnostic view is not. *Fix:* Either cap or purpose-limit FR-22 (no bulk audit/reference dump, no confirmed-resolution roster without export permission) or retract the “alternatives to unbounded troubleshooting” claim and treat FR-24 as a shareable snapshot of data FR-22 already grants.

- **medium** Pre-activation “safe status” can leak reserved workspace intent (FR-1, FR-2, FR-5, FR-22) — FR-2/FR-5 hide pre-activation work from open/list. FR-22 lets Operators/Administrators “inspect their safe status.” “Safe” is undefined. A status payload that includes proposed name, reserved Project id, Folder plan, attachment ids, or initiating Conversation id is a diagnostic channel around folder-gated activation and around Chatbot’s “creates nothing before confirmation” (FR-15). *Fix:* Define the pre-activation allow-list: task id, Task Status, safe reason/recovery codes, expiry. No reserved Project identity, names, Folder/File/Memory ids, Setup, or Conversation ids until Read-Model-Confirmed Completion.

- **medium** FR-12 `Denied` vs `NoMatch` can distinguish a foreign Conversation (§5, FR-12, NFR-1) — §5 `Denied` “discloses no protected Project/component metadata” but is still a distinct Context Response State from `NoMatch`. FR-12 returns those results for “a Conversation with no explicit Project.” An actor who guesses or recycles a Conversation id learns whether the resource exists and is unauthorized versus exists and has no Project. That is a cross-Tenant/cross-actor existence oracle. *Fix:* For unauthorized or cross-Tenant Conversation inputs, collapse `Denied` and `NoMatch` (and nonexistence) into one actor-visible outcome with no Project/component fields, consistent with fail-closed resolution.

- **medium** File/Memory links escape the Folder authorization anchor (FR-8, FR-9, FR-10, FR-16) — FR-9: “File References are optional and do not replace the Project Folder” and may be linked “without changing the Project Folder.” Authorization “remains delegated” to Folders/Memories. A Project User can therefore assemble FR-16 context from files and Memories that never sat in the Project Folder — including resources authorized to the actor in another Project’s Folder. The “stable authorization anchor” does not bound context membership. *Fix:* Require File References to be descendants of the bound Project Folder, or require confirmation that names the foreign Folder/Project and re-checks that authorization on every context assembly.

- **low** FR-19 “rejects secrets” has no detection rule (FR-3, FR-19, NFR-1) — Setup “rejects secrets, unrestricted paths, and foreign payloads” and “Failures identify safe field/reason codes without echoing sensitive values.” There is no definition of a secret, so users will paste tokens into “user-facing instructions,” after which FR-16 and FR-22 will serve them as authorized metadata. *Fix:* Define rejectable classes (key-shaped tokens, `sk-`/`Bearer` prefixes, PEM blocks, known secret references) and treat residual Setup as sensitive: never export, never operator-default-read, never put in traces or audit.

- **low** Idempotency scope can cross Projects for the same actor (glossary, NFR-4, FR-1) — An Idempotency Key is “scoped to Tenant, actor, and operation,” not Project or target. Equivalent reuse “returns the original Durable Task.” A caller who reuses a key on a different Project receives another Project’s task identity and status — a metadata leak and a confirmation-bypass if that task was a silent link. *Fix:* Include action targets (Project, Conversation, Folder) in the idempotency scope, or treat target mismatch as a conflict without returning the original task body.
