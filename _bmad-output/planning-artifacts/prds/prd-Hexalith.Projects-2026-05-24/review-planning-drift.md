# Planning-Drift Review — Hexalith.Projects

## Overall verdict

`prd.md` (status `final`, updated 2026-07-15) still holds the approved v1 product contract: FR-1–FR-24, NFR-1–NFR-11, the §3.2 roles, the §5 response/recovery vocabulary, and the §2.3 release-cut rule. Later approved sprint-change proposals from 2026-07-31 through 2026-09-02 consistently claimed “no PRD change” / “no semantic change,” did not remumber or retire any FR/NFR, rejected MVP scope reduction, and used UX/epic edits to restore the existing confirmation and role rules rather than replace them. The PRD folder is nonetheless stale as a *current planning baseline*: `.memlog.md` last records an SCP reconcile on 2026-07-17; `addendum.md` ingested only the 2026-08-02 rerun-3/4 provenance path (E-15–E-18); and `prd.md` §2.5 still reads as if UX, architecture, and epic decomposition have no phase-blocking questions, which conflicts with the addendum’s E-17 `NOT READY` freeze and with later SCP work that materially corrected those downstream artifacts.

## Findings

- **high** `prd.md` §2.5 readiness wording conflicts with addendum current disposition (`prd.md` §2.5; `addendum.md` “Current Readiness…”) — §2.5 states that no phase-blocking *product* questions remain for UX, architecture, or epic decomposition, and frontmatter still presents the PRD as `final` / 2026-07-15. The addendum’s current implementation disposition is E-17 `NOT READY` (`implementation-readiness-report-2026-08-02-rerun-4.md`): production-authority implementation remains frozen until the Story 6.1 prerequisite chain, signed same-baseline architecture conformance, P4 clean-checkout, story-spec readiness, and an independent `READY` rerun all pass; production release additionally requires Story 8.11 and Jerome/John’s dated disposition. E-6 still records live Playwright 19 passed / 56 failed. Later approved proposals (`sprint-change-proposal-2026-08-01-implementation-readiness-correction.md`, `sprint-change-proposal-2026-08-01-implementation-readiness-rerun-correction.md`, `sprint-change-proposal-2026-08-01-implementation-readiness-rerun-2-correction.md`, `sprint-change-proposal-2026-08-02.md`, `sprint-change-proposal-2026-08-02-implementation-readiness-rerun-4.md`) found over-broad UX confirmation, four UX-alignment defects, missing architecture sign-off, and Epic 8 cohesion / two-track gaps — i.e. UX/architecture/epic *artifacts* were not settled even though the product IDs were. A reader of `prd.md` alone would start those phases as unblocked; a reader of the addendum would not start production implementation. The second sentence of §2.5 (verify addendum gates before stories start) only partially mitigates this, because it names repository/version mechanisms and does not warn that later SCPs treated UX and epic decomposition as defective relative to this same PRD. This is document-status / phase-gate drift, not an FR rewrite, but it is the highest-impact way this PRD can be misused as the current baseline. *Fix:* Keep FR/NFR text; revise §2.5 (and only §2.5) so planning-status language matches addendum E-17 / Story 8.11 / live 19/56 and points to later unreconciled SCPs; do not let “no product questions remain for UX/architecture/epics” stand as a green light.

- **medium** 2026-08-02 claimed no PRD change while binding export retry/admission semantics the PRD never states (`sprint-change-proposal-2026-08-02.md` §4.3 and Story 8.2 AC; `prd.md` FR-24, NFR-4, NFR-6) — The 2026-08-02 proposal lists PRD/addendum disposition as “Complete product baseline; no semantic change,” then (1) classifies `safe-diagnostic-export.create` as a *synchronous read* with no Confirmation Artifact and no Durable Task, and (2) replaces Story 8.2’s “does not double-produce” lost/duplicate rule with: if no separately approved export-idempotency contract exists, a repeated or lost request may produce a *new current snapshot*; adapters must not claim exactly-once or return retained bytes. They do **not** say export is outside the Durable Task / NFR-4 equivalent-retry contract. Leaving it only in epics/UX while telling readers the PRD is unchanged is dangerous silence for architecture and API contracts. Latest readiness (`implementation-readiness-report-2026-08-02-rerun-4.md`) already treats “synchronous/non-retained” export as aligned with the PRD. *Fix:* Either add one FR-24/NFR-6 consequence (export is a bounded synchronous operation, not a Durable Task; lost/repeat requests mint a new snapshot and a new audit attempt) or record that exact implication in the addendum so `prd.md` is not silently outranked by Story 8.2.
